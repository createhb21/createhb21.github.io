"TS 0%에서"

내 메모에 남은 짧은 문장이지만, 당시 팀 분위기를 가장 정확하게 설명한다.

빠르게 기능은 나가는데,
다음 스프린트가 시작될 때마다 모두가 같은 말을 했다.

- “여기 건드려도 돼?”
- “이 값 null 올 수도 있지?”
- “배포해도 안전해?”

타입이 없으면 속도가 빠르다는 말은 반만 맞다.
변경이 누적되면 속도는 결국 빚이 된다.

---

전면 전환은 처음부터 포기했다.
그 대신 전환 순서를 설계했다.

먼저 바꾼 곳:

- API 응답 경계
- 공용 유틸
- 상태 모델의 핵심 타입

나중에 바꾼 곳:

- 단순 표시 컴포넌트
- 변동이 잦은 실험 UI

즉, “자주 깨지는 경계”부터 잠갔다.

---

실패했던 시도도 있다.

초기에 `strict`를 과하게 올렸다가,
PR이 타입 수정만으로 가득 차서 도메인 리뷰가 멈췄다.

그 뒤로는 방식이 바뀌었다.

- 규칙은 단계적으로 강화
- `any`는 금지 대신 “임시 타입”으로 부채 추적
- 마이그레이션 체크리스트를 피처 완료 조건에 포함

타입 전환을 별도 프로젝트가 아니라,
일상 개발의 일부로 흡수했다.

---

결과적으로 가장 크게 바뀐 건 오류 위치였다.

- 예전: 런타임에서 늦게 발견
- 이후: 컴파일/리뷰 단계에서 조기 발견

팀 대화도 바뀌었다.

예전엔 null 방어 코드 얘기가 많았고,
지금은 비즈니스 규칙 얘기가 많다.

TS 전환은 문법 변경이 아니라,
팀의 불확실성을 줄이는 장치였다.
