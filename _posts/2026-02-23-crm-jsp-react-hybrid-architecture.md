"레거시를 버리고 새로 가자"는 말은 멋있다.
하지만 운영 시스템에서 그 말은 종종 비현실적이다.

CRM 전환이 그랬다.

- 기존 JSP 기능은 살아 있어야 했고
- 신규 요구는 계속 들어왔고
- 다운타임은 허용되지 않았다.

그래서 빅뱅 전환은 선택지가 아니었다.

---

우리가 택한 전략은 공존이었다.

JSP를 완전히 없애지 않고,
세션/라우팅 shell로 남긴 뒤,
신규 도메인부터 React를 주입했다.

요점은 기술 혼합이 아니라 경계 설계였다.

- 어디까지는 JSP 책임인지
- 어디부터 React 책임인지
- 실패 시 어떻게 되돌릴지

이 경계를 코드와 운영 문서에 동시에 남겼다.

---

점진 전환에서 가장 위험한 건 “애매한 중간 상태”다.

그래서 피처 단위로 전환 순서를 고정했다.

- 영향이 큰 코어 화면은 뒤로
- 독립도 높은 신규 기능은 앞으로

이 순서 덕분에 운영 안정성을 지키면서,
신규 개발 생산성도 놓치지 않을 수 있었다.

마이그레이션은 기술 쇼케이스가 아니다.
현업에서는 언제나 “오늘도 돌아가야 한다”가 1순위다.

## 하이브리드 전환에서 실제로 쓴 경계 설계

JSP와 React 공존은 기술 혼합보다 계약 설계 문제에 가깝다. 가장 먼저 정한 건 "어떤 책임이 어느 레이어에 남는가"였다. 세션/초기 라우팅/레거시 화면 진입은 JSP shell, 신규 피처 렌더링과 상태 관리는 React로 명확히 분리했다.

전환 전략은 Strangler Fig 패턴을 기반으로 잡았다. 기존 시스템을 한 번에 교체하지 않고, 가장 바깥의 새 기능부터 감싸며 점진적으로 대체하는 방식이다([Strangler Fig Application](https://martinfowler.com/bliki/StranglerFigApplication.html)). 이 방식의 장점은 실패 반경이 작다는 점이다. 특정 피처가 문제를 일으켜도 전체 시스템을 되돌릴 필요가 없다.

또 하나 중요했던 건 계약 테스트였다. 레거시와 신규가 같은 API 계약을 공유하지 않으면, 전환 속도보다 회귀 속도가 더 빨라진다. 그래서 Consumer-Driven Contract 접근을 참고해([Consumer Driven Contracts](https://martinfowler.com/articles/consumerDrivenContracts.html)) 경계 API를 우선 고정했고, 팀별 검증에는 Pact 문서를 참조해 테스트 기준을 맞췄다([Pact docs](https://docs.pact.io/)).

설정 관리도 정리했다. 환경별 엔드포인트/기능 토글/브랜드 옵션을 코드 분기 대신 런타임 설정으로 이동시켜, 12-Factor의 config 분리 원칙을 적용했다([12-Factor Config](https://12factor.net/config)). 이 선택은 배포 빈도가 올라갈수록 효과가 크게 나타났다.

결과적으로 하이브리드 구조의 핵심은 "둘 다 유지"가 아니라 "둘의 경계를 안정적으로 운영"하는 데 있었다. 전환 성공은 기술 스택보다 계약 품질에서 결정됐다.

## 전환을 진행하면서 제가 조심하려고 했던 태도

레거시를 다루다 보면 저도 모르게 "이건 빨리 바꿔야 해"라는 조급함이 앞설 때가 있었다. 그런데 운영 중인 CRM에서는 그 조급함이 곧 리스크가 됐다. 사용자 입장에서는 기술 부채보다 "오늘 업무가 멈추지 않는 것"이 더 중요하기 때문이다. 그래서 제가 스스로 다잡은 기준은 "기술적으로 맞는 방향"보다 "운영상 감당 가능한 속도"였다.

특히 JSP와 React를 함께 가져가는 구간에서는 완성도보다 일관성이 더 중요했다. 같은 화면에서도 일부는 JSP, 일부는 React로 동작하니, 개발자 입장에서는 불편하고 비효율적으로 느껴질 수 있다. 하지만 이 불편함을 견딘 덕분에 전체 다운타임 없이 전환을 이어갈 수 있었다. 이 과정에서 제가 배운 건, 좋은 아키텍처는 깔끔함만으로 평가되지 않는다는 점이다. 실제 운영 제약을 흡수할 수 있어야 좋은 아키텍처라고 부를 수 있다.

전환 중반에는 팀 내부 피로도도 크게 올라갔다. 기존 코드를 고치면서 동시에 새 코드를 만들어야 하니, 리뷰 기준이 흔들리고 테스트 우선순위도 자주 바뀌었다. 그래서 기술 전략과 별개로 "팀의 리듬"을 관리해야 했다. 저는 이 시기에 리뷰 정책을 단순화했다. 한 PR에서 구조 변경과 기능 추가를 동시에 하지 않도록 제한하고, 경계 변경 PR은 리뷰어를 늘려 의사결정 부담을 분산했다. 속도는 잠깐 느려졌지만, 사고는 확실히 줄었다.

아직도 이 접근이 절대 정답이라고 말하기는 어렵다. 프로젝트 성격에 따라 전면 전환이 더 나은 경우도 있다. 다만 제가 경험한 CRM에서는 점진 전환이 조직의 인지 부하와 운영 리스크를 가장 낮추는 선택이었다. 이 글을 읽는 분들께도 "무엇이 더 현대적인가"보다 "무엇이 우리 서비스에 덜 위험한가"를 먼저 질문해보시길 권하고 싶다.

## 전환 이후 남긴 운영 표준(재사용 가능 버전)

제가 다음 프로젝트에서도 재사용하려고 남겨둔 표준은 아래 네 가지다.

1. **경계 계약서(Interface Charter)**
- JSP shell이 책임지는 범위
- React 영역이 책임지는 범위
- 예외 시 fallback 경로

2. **릴리즈 안정화 룰**
- 신규 전환 피처는 feature flag로 감싸기
- 전환 피처의 rollback 경로 사전 점검
- 배포 전 legacy 연동 테스트 필수

3. **테스트 우선순위 룰**
- 경계 API 계약 테스트 우선
- 핵심 사용자 플로우 E2E 최소 세트 유지
- 스냅샷 테스트는 상태 수를 줄여 유지비 통제

4. **커뮤니케이션 룰**
- 전환 진행률을 코드량이 아니라 운영 위험도로 보고
- 장애 가능성이 높은 변경은 사전 공유
- "왜 이 전환 순서를 택했는지"를 문서로 남기기

지금 돌아보면 기술적으로 가장 큰 성과는 React 도입 자체가 아니라, 전환 기간 내내 서비스 신뢰를 지켰다는 점이었다. 그리고 그 신뢰는 화려한 리팩터링보다 작은 운영 원칙을 꾸준히 지키는 데서 나왔다.
