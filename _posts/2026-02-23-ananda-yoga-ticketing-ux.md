티켓팅은 오픈 버튼을 누르는 순간부터 전쟁이다.

트래픽이 몰리는 건 예상했지만,
진짜 문제는 다른 데 있었다.

사용자가 중간에 포기했다.

---

분석해보니 원인은 세 가지였다.

- 초반 입력 항목이 너무 많고
- 실패 메시지가 추상적이고
- 로딩 지연의 의미가 전달되지 않았다.

우리는 “속도를 올리자”보다 먼저
“사용자가 무엇을 불안해하는지”부터 봤다.

---

바꾼 포인트는 꽤 작았다.

- 단계 진행률을 눈에 보이게 표시
- 필수 입력만 먼저 받는 흐름으로 재배치
- 실패 문구를 재시도 가능한 언어로 변경
- 로딩 중 현재 단계 설명 추가

기술적으로는 소소해 보여도,
퍼널에서는 치명적인 마찰을 줄였다.

---

결과는 숫자로도 확인됐다.

- 티켓팅 완주율이 개선됐고
- 이벤트 오픈 안정성이 올라갔고
- 앱 스토어 순위가 10위권까지 올라갔다.

개발자로서 가장 기억에 남는 건 이것이다.

UX 개선은 감각이 아니라,
사용자 불안을 줄이는 구조 설계였다.

## 퍼널 개선을 기술/문구/실패복구로 분해한 이유

티켓팅 UX에서 성능 최적화만으로는 완주율이 잘 오르지 않았다. 사용자가 떠나는 지점은 느림 자체보다 "내가 지금 뭘 기다리는지 모르겠다"는 불안에서 많이 발생했다. 그래서 퍼널 개선을 화면 속도, 문구, 실패 복구로 분해했다.

먼저 체크아웃 UX 원칙을 다시 읽고 흐름을 재설계했다. NN/g의 체크아웃 가이드에서 반복되는 메시지는 단계 가시성과 오류 복구의 명확성이다([Checkout UX](https://nnngroup.com/articles/checkout-ux/)). 이를 반영해 진행률 표기를 넣고, 실패 시 에러 문구를 "무엇이 문제인지"와 "다음 행동"까지 포함하는 형태로 바꿨다([Error Message Guidelines](https://nnngroup.com/articles/error-message-guidelines/)).

기술 쪽에서는 체감 성능을 Core Web Vitals 관점으로 분해했다. 단순히 번들 크기를 줄이는 대신, LCP 구간의 주요 리소스를 당기고([LCP](https://web.dev/articles/lcp)), 레이아웃 이동이 많은 컴포넌트는 고정 박스 전략으로 바꿨다([CLS](https://web.dev/articles/cls)). 전체 기준은 [Web Vitals](https://web.dev/articles/vitals) 문서를 따라 측정 지표를 공통화했다.

결제/예약 재시도 구간은 멱등 설계를 적용해 중복 처리 불안을 줄였다. 사용자에게는 "다시 시도" 버튼이지만, 서버에는 동일 요청으로 처리돼야 하기 때문이다([Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests)). 이 원칙이 없으면 UX 개선을 해도 운영 CS가 줄지 않는다.

결론적으로 완주율은 UI 감성만으로 오르지 않았다. 가시성, 예측 가능성, 재시도 안전성, 성능 지표가 함께 올라갈 때 의미 있는 개선이 나왔다.

## 제가 다음 시즌 오픈 전에 꼭 다시 보려는 개선 항목

이 프로젝트를 정리하면서 스스로 가장 많이 되묻는 질문은 "우리가 사용자 불안을 충분히 줄였는가"다. 수치가 좋아졌다는 사실은 분명 고무적이지만, 그 수치가 언제든 다시 떨어질 수 있다는 점도 함께 기억하려고 한다. 이벤트 도메인은 계절성, 유입 경로, 기기 분포가 바뀌면 같은 화면도 전혀 다르게 반응하기 때문이다.

먼저 저는 "입력 부담"을 더 줄일 방법을 검토하고 있다. 현재도 단계 분할을 적용했지만, 신규 사용자는 용어 자체에서 막히는 경우가 있었다. 그래서 다음 버전에서는 입력 항목의 우선순위를 더 명확히 나누고, 필수 정보와 선택 정보를 시각적으로 구분해 첫 진입 피로를 낮출 계획이다. 개인적으로는 이 부분이 디자인 감각보다 정보구조 설계에 더 가깝다고 생각한다.

둘째로, 실패 시나리오에서 안내 문구를 더 정교하게 만들고 싶다. 지금 문구도 이전보다 개선됐지만, 네트워크 불안정/재시도 충돌/세션 만료처럼 원인이 다른 실패를 동일한 어조로 안내하면 사용자는 여전히 불안을 느낀다. 그래서 실패 원인별로 "현재 상태", "자동 처리 여부", "사용자 행동"을 고정된 포맷으로 보여주려 한다. 작은 차이 같지만, CS에서 전달되는 톤을 크게 바꾼 경험이 있어 우선순위를 높게 보고 있다.

셋째로, 퍼널 지표 해석 방식도 개선하려고 한다. 지금까지는 단계별 이탈률을 중심으로 봤지만, 같은 이탈이라도 "지연 후 이탈"과 "즉시 이탈"은 원인이 다르다. 다음 분석에서는 시간축을 함께 붙여 원인을 더 정확히 분리하려 한다. 특히 로딩 구간에서의 체감 불확실성을 줄이는 방향으로 실험을 설계해 보려 한다.

넷째로, 운영팀과의 피드백 루프를 더 짧게 가져가고 싶다. 이벤트 오픈 당일에는 개발팀보다 운영팀이 사용자 반응을 먼저 본다. 그런데 이 피드백이 주간 단위로만 공유되면 개선 타이밍을 놓친다. 앞으로는 오픈 당일 2~3회 짧은 싱크를 잡아, 즉시 수정 가능한 항목은 당일 반영하고 구조적 이슈만 백로그로 넘기는 방식으로 바꿀 예정이다.

제가 이 글에서 조심하고 싶은 건 "성공했다"는 결론을 너무 쉽게 내리지 않는 것이다. 좋은 결과가 있었던 건 사실이지만, 서비스 경험은 살아 있는 대상이라 늘 맥락이 바뀐다. 그래서 저는 이번 사례를 성취라기보다, 다음 시즌을 위한 기준선으로 보고 있다.

## 현장에서 바로 적용 가능한 티켓팅 QA 체크리스트

- 오픈 30분 전: 주요 퍼널 API 응답 시간/오류율 점검
- 오픈 직후: 1분/5분 단위 이탈 급증 구간 확인
- 오류 메시지: 실패 원인별 안내 문구 표준화 여부 점검
- 재시도 흐름: 동일 요청 중복 처리 방지 확인
- 모바일 저사양: 입력/스크롤/결제 버튼 지연 체감 테스트
- 운영 공지: 장애 시 즉시 노출 가능한 안내 템플릿 준비

이 체크리스트도 완성형은 아니다. 다만 반복 운영 속에서 더 보완할수록 팀 전체의 안정감이 올라간다는 점은 분명히 느꼈다.
